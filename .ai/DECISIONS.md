# Architecture Decisions

## D001 — Shared project context belongs in the repository
The repository is the shared memory layer between different AI agents. Agents must not depend on one agent remembering another agent's chat history.

## D002 — Git is the synchronization source of truth
Changes made locally must be committed and pushed before another agent using the GitHub copy can reliably see them. Local uncommitted changes remain local.

## D003 — Generic pipeline over request-specific hacks
Natural-language requests must be handled through generic understanding, knowledge retrieval, planning, deterministic generation, and validation. Individual examples must not become special-case code.

## D004 — Minecraft version awareness
Minecraft Java 1.21.11 is the current target. Minecraft syntax and data must be treated as version-specific where behavior or format differs.

## D005 — Deterministic generation after AI planning
AI should interpret and plan the request, but datapack files should be generated by deterministic code from a validated structured plan. This makes generated output reproducible and easier to validate.

## D006 — Validation and repair are first-class stages
Generated datapacks should be validated/tested. When validation fails, structured errors should feed an AI repair loop rather than relying on blind regeneration.

## D007 — Local-first model strategy
The project should support local Ollama inference where practical, avoiding a mandatory external API key. Model/resource choices must account for the development machine's RAM limits.

## D008 — Java 1.21+ datapack conventions: pack_format 94 and singular directory names
Minecraft Java 1.21.11 uses `pack_format: 94` (verified from server release metadata). In 1.21+, data directories use singular registry names matching the registry identifier (e.g. `data/<namespace>/loot_table/` rather than `loot_tables`). Datapack generator implementations must adhere strictly to these conventions.

## D009 — Deterministic validation and repair separation
The Validator layer must remain strictly deterministic, using schema parsing, security checks, and knowledge verification without LLM calls or automated repair. Any automated fixes belong exclusively to the AI Repair Loop (Step 7) consuming structured validator output.

## D010 — Structured AI Repair Loop with Deterministic Generator & Validator Contract
The AI Repair Loop (`repair/`) never writes arbitrary datapack files directly. When validation fails, the AI receives structured validator errors, original understanding requirements, previous plans, and retrieved Minecraft knowledge to output a structured `RepairPlan` (containing diagnostic reasoning and corrected planner specifications/modifications). The corrected plan is fed into the deterministic generator, and the regenerated datapack is validated again. The repair loop enforces configurable retry limits (default 3) to prevent infinite loops, records full diagnostic history for every attempt, and short-circuits immediately if initial validation succeeds.

## D011 — Minecraft Java 1.21.11 Pack Format Audit & Dual Compatibility (94 / 94.1)
An audit of authoritative Minecraft Java Edition 1.21.11 metadata (`versions/1.21.11/server-1.21.11.jar`'s `version.json` and internal vanilla `pack.mcmeta`) confirms that 1.21.11 defines `data_major: 94` and `data_minor: 1`, representing Data Pack version 94.1. The vanilla server pack specifies `pack_format: 94`, `min_format: [94, 0]`, and `max_format: [94, 1]`. To ensure full backward compatibility with integer-only parsers while strictly complying with 1.21.11 range-aware validators, `DatapackManifest` and `DatapackGenerator` generate `pack.mcmeta` with integer `pack_format: 94` alongside explicit `min_format: [94, 0]` and `max_format: [94, 1]`. The `DatapackValidator` accepts both standard integer 94 and format array representations matching `[94, 1]`.

## D012 — End-to-End Pipeline Orchestration & Clarification Guardrails (Step 8)
The pipeline orchestrator (`pipeline/`) integrates all 7 stages: Understanding → Minecraft RAG Retrieval → Planning → Deterministic Generation → Deterministic Validation → AI Repair Loop (if invalid) → Validated Datapack ZIP Output. Key architectural guardrails include:
1. Early Exit on Clarification: If Understanding or Planner returns `status == "needs_clarification"` or specifies clarification questions, the pipeline immediately halts and returns a structured clarification result without calling the generator or writing any disk files.
2. Repair Exclusivity: AI repair is ONLY invoked when deterministic validation fails (`val_result.is_valid == False`). Clean datapacks skip repair completely (0 attempts).
3. Zero-Failure Delivery Guarantee: The pipeline must NEVER return an invalid datapack or ZIP as successful. If repairs are exhausted or fail, structured diagnostics and attempt history are returned under `status: "failed"`.
4. ZIP Validation Checkpoint: When ZIP creation is enabled, the final ZIP archive is independently verified by the validator before final pipeline success is reported.

## D013 — Web Interface Decoupling & Direct Pipeline API Consumption (Step 9)
The user-facing web interface (`web/`) is built as a clean, decoupled layer on top of the public pipeline API (`pipeline.run_minecraft_pipeline`). It does not alter, replace, or wrap internal pipeline abstractions. Key architectural rules:
1. Complete Decoupling: Web endpoints (`/api/generate`, `/api/download/{filename}`, `/api/health`) purely consume the existing `PipelineResult` data contract and expose it via JSON to the frontend.
2. Zero Frontend Build Overhead: The UI uses standard HTML5, Vanilla CSS (modern Obsidian & Emerald dark theme), and Vanilla JS without requiring Node.js, npm bundles, or external runtime compilers.
3. Path Traversal Guard: Direct ZIP download is isolated to the `generated/` directory using strict regex matching (`^[a-zA-Z0-9_\-\.]+\.zip$`) and path resolution checks to prevent directory traversal.
4. Preserved CLI Parity: The existing CLI entry point (`run_pipeline.py`) remains fully functional and independent of the web server.

## D014 — Multi-Mechanism Datapack Generator Architecture (Step 10)
To expand beyond single-mechanism loot table generation while strictly preserving deterministic behavior and avoiding LLM command hallucination:
1. Mechanism Abstraction: The generator dispatches to dedicated mechanism generators inheriting from `BaseMechanismGenerator`. Each mechanism accepts a structured definition model (`LootTableModification`, `FunctionDefinition`, `FunctionTagDefinition`, `AdvancementDefinition`) and deterministically produces `DatapackResource` objects containing relative paths and serialized content.
2. Separation of Concerns: The Planner states WHAT mechanisms are required; the Generator's mechanism extractors and generators determine HOW to structure and serialize datapack files.
3. 1.21.11 Path Strictness: All mechanisms conform to Java 1.21+ singular path conventions (`loot_table/`, `function/`, `tags/function/`, `advancement/`). The validator actively rejects legacy plural directories (`loot_tables/`, `functions/`, `tags/functions/`, `advancements/`) with `OBSOLETE_PATH`.
4. Command Sanitization in Functions: Commands in `.mcfunction` files cannot have leading `/` characters; the `FunctionMechanismGenerator` automatically normalizes commands by stripping leading slashes, and `DatapackValidator` verifies this rule with `LEADING_SLASH_IN_FUNCTION`.
5. Deterministic Composability: Multiple mechanisms can be generated together into a single unified datapack. ZIP archives are deterministically hashed using fixed timestamps and sorted directory traversal.

## D015 — Structured Planner → Generator Mechanism Specifications (Step 11)
To establish a machine-readable boundary between the AI Planner and Deterministic Generator without vague natural-language interpretation or duplicate knowledge:
1. Typed Mechanism Specifications: The Planner produces `ImplementationPlan` objects containing a list of `MechanismSpecification` models (defined in `generator/models.py` and exported by `ai/planner.py`). Rather than loose natural-language descriptions, specifications provide explicit typed parameters (`target`, `item`, `count`, `operation`, `commands`, `namespace`, `path`, `tag_name`, `values`, `criteria`, `rewards`, `display`).
2. Knowledge Externalization: The Planner schema does not duplicate Minecraft database facts. Minecraft-specific facts continue to originate exclusively from `knowledge/` (entities, items, commands, loot tables), which the Planner references to populate typed parameters.
3. Completeness & Validation Contract: `validate_mechanism_specification()` deterministically verifies completeness for each mechanism type (e.g. loot tables must have `target` and `item`; functions must have `path` and non-empty `commands`; function tags must have `tag_name` and non-empty `values`; advancements must have `path` and non-empty `criteria`). Incomplete specifications are rejected prior to generation without LLM involvement.
4. Direct Generator Consumption: `DatapackGenerator.extract_mechanisms()` directly maps `MechanismSpecification` objects into deterministic mechanism definitions (`to_loot_modification()`, `to_function_definition()`, `to_tag_definition()`, `to_advancement_definition()`), eliminating heuristic regex and text scraping while maintaining backward compatibility for legacy minimal plans.
5. Generality & Dynamic Clarification: Ambiguous requests continue to halt early at Understanding/Planner clarification without premature generation. All arbitrary mob/item/command combinations are handled generically without special-cased if/else logic.

## D016 — Custom Recipe Mechanism Generation & Validation (Step 12)
To expand deterministic datapack generation to crafting and smelting without duplicating knowledge or violating Minecraft Java 1.21.11 standards:
1. First-Class Datapack Registry: Custom recipes are implemented as a dedicated mechanism generator (`RecipeMechanismGenerator` inheriting from `BaseMechanismGenerator`), emitting resources to `data/<namespace>/recipe/<name>.json`.
2. 1.21.11 Format Precision: Follows the modern 1.21+ result structure (`{"id": "minecraft:<item>", "count": <int>}`), completely replacing legacy pre-1.21 `{"item": ...}` format. Strictly enforces singular `recipe/` directory paths, and the validator flags legacy `recipes/` with `OBSOLETE_PATH`.
3. Multi-Serializer Support: Supports shaped crafting (`minecraft:crafting_shaped`), shapeless crafting (`minecraft:crafting_shapeless`), smelting (`minecraft:smelting`), blasting (`minecraft:blasting`), smoking (`minecraft:smoking`), campfire cooking (`minecraft:campfire_cooking`), and stonecutting (`minecraft:stonecutting`).
4. Static Deterministic Validation: `DatapackValidator` verifies recipe JSON structure, checks that all pattern symbols in shaped recipes match defined keys, and deterministically validates all input ingredient item IDs and output result item IDs against the authoritative 1.21.11 item knowledge base (`valid_items`).
5. Unified Composition: Custom recipes compose seamlessly with all existing mechanisms (loot tables, functions, function tags, advancements) in single composite datapacks with byte-for-byte reproducible ZIP archives.

## D017 — Generic Custom Predicate Mechanism Generation & Validation (Step 13)
Authoritative investigation of `versions/1.21.11/server-1.21.11.jar` (bytecode registry class `fro.class`) confirms 19 valid condition types in Minecraft Java Edition 1.21.11: `inverted`, `any_of`, `all_of`, `random_chance`, `random_chance_with_enchanted_bonus`, `entity_properties`, `killed_by_player`, `entity_scores`, `block_state_property`, `match_tool`, `table_bonus`, `survives_explosion`, `damage_source_properties`, `location_check`, `weather_check`, `reference`, `time_check`, `value_check`, and `enchantment_active_check`.
To support custom predicates generically and deterministically:
1. 1.21.11 Directory Structure: Custom predicates reside strictly under `data/<namespace>/predicate/<path>.json` (singular `predicate/`). The validator actively catches legacy plural `data/<namespace>/predicates/` with `OBSOLETE_PATH`.
2. Typed Mechanism Specification Boundary: Rather than generating raw JSON in the Planner, the Planner produces a structured `MechanismSpecification` (`type: "predicate"`) containing explicit fields: `path`, `condition_type`, `condition_params`, `terms`, and `term`. `to_predicate_definition()` maps this to a validated `PredicateDefinition` model in `generator/models.py`.
3. Deterministic Predicate Generator: `PredicateMechanismGenerator` (`generator/mechanisms/predicate_mech.py`) transforms structured parameters into exact Minecraft JSON, supporting core environmental checks (`weather_check`, `time_check`, `location_check`), probabilities (`random_chance`), player/entity flags (`entity_properties`), tool checks (`match_tool`), references (`reference`), and recursive nested logical trees (`all_of`, `any_of`, `inverted`). Outputs are sorted and formatted for byte-identical determinism.
4. Static Deterministic Validation: `DatapackValidator` verifies predicate file location under `data/<ns>/predicate/`, parses JSON, verifies that `condition` is in the authoritative 1.21.11 condition registry, validates condition-specific parameters (e.g. chance float bounds 0.0–1.0, non-empty terms for composite conditions), and checks referenced item IDs and entity IDs against the 1.21.11 knowledge base (`valid_items`, `valid_entities`).
5. Generality & Composition: Predicate generation contains zero entity/item/phrase hardcoding, works for arbitrary user requests, and composes cleanly with all existing mechanisms (`loot_table`, `function`, `function_tag`, `advancement`, `recipe`) in unified datapack packages.

## D018 — Global vs Per-Player State Machines and Load Function Execution Semantics (Step 13 Runtime Integration)
Investigation of real Minecraft Java 1.21.11 runtime integration failures (Step 13) revealed fundamental execution context semantics in the server engine (`versions/1.21.11/server-1.21.11.jar` bytecode: `ani.class` `ServerFunctionManager`, `aox.class` `ExecuteCommand`, `frw.class` `WeatherCheck`, `axf.class` `ServerLevel`):
1. Load Function Timing: `#minecraft:load` executes on server boot or `/reload` before players connect. Commands targeting `@a` in load functions evaluate against an empty selector (`Can't get value of ... for MockPlayer; none is set`), leaving joining players with unset scoreboard scores.
2. Global Environmental vs Per-Player State: Environmental states (weather, time, dimension properties) are global game-level states. Tracking global transitions using per-player scoreboard iterations (`execute as @a ...`) leads to player join/leave desynchronization and missed events. Global environmental events MUST use a persistent global score holder (e.g. `#global` or `#state`), initialized safely during `#minecraft:load` (`scoreboard players set #global <obj> 0`).
3. Execution Context Chaining: To target online players from a global state condition, commands must explicitly chain context: `execute if score #global <obj> matches 0 if predicate <pred> as @a at @s run <action>`.
4. Per-Player State Initialization: When states are genuinely per-player (e.g. player movement, sneak status, individual cooldowns), scores cannot be initialized in `#minecraft:load` via `@a`. Instead, they must be dynamically initialized in the tick function: `execute as @a unless score @s <obj> matches 0..1 run scoreboard players set @s <obj> 0`.
5. Static Validation vs Runtime Simulation Boundary: Offline static datapack validation cannot simulate the 20Hz server game loop, player network joins, or continuous world physics. However, the static validator CAN and MUST detect anti-patterns such as `EMPTY_SELECTOR_ON_LOAD` (using player selectors `@a`, `@p`, `@r`, `@e[type=player]` in load functions to set scores or tags). Planner system prompt rules 24 & 25 enforce correct generic state machine architecture for both global and per-player state patterns without hardcoding specific phrases or mechanisms.

## D019 — Autonomous Datapack QA, Intent Verification & Auto-Repair Architecture (Step 14)
To ensure that generated datapacks are not merely structurally well-formed but actually fulfill user intent and execute correctly at runtime without regressions:
1. Strict Separation of Concerns: `DatapackValidator` remains strictly responsible for deterministic structural validation (JSON syntax, pack.mcmeta, registry directories, 1.21.11 item/entity IDs). The `qa` package (`qa/`) is independently responsible for deep semantic review, cross-file reference graphs, execution-context reasoning, state-machine temporal logic, and intent verification.
2. Complete Pack Review: QA inspects every generated resource in the datapack, detecting orphaned resources, missing references (tags→functions, functions→predicates, undeclared scoreboard objectives), unanchored entity commands (`give @s` without `as`), spatial commands missing `at @s`, and state machine bugs (ordering race conditions, missing reset triggers).
3. Structured Repair via Deterministic Regeneration: When QA detects errors, the AI Diagnosis & Repair layer (`QARepairEngine`) diagnoses the failure and outputs a structured `QARepairPlan` with updates to planner `MechanismSpecification` objects. The system NEVER allows the LLM to write or patch arbitrary datapack files directly; the deterministic generator regenerates the complete pack, preserving byte-level reproducibility.
4. Bounded QA Loop with Repeat Detection: The QA repair loop enforces a maximum attempt count (default 3). If an identical set of error findings repeats across attempts without progress, the loop immediately halts with `verification_failed` to prevent infinite repair cycling.
5. Strict Final READY Gate: A datapack is marked `READY` and `verified` ONLY if structural validation = PASS, QA review = PASS, intent verification = PASS, and runtime simulation = PASS.
6. Runtime Testing Abstraction: `RuntimeTestRunner` provides a modular testing boundary with modes (`unavailable`, `static_simulation`, `minecraft_server`). The static simulation verifies discrete tick lifecycles (boot load, player joins, transition triggers, and state resets) without requiring external processes, while allowing headless server harnesses to plug in cleanly.
